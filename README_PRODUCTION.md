# Poytakht CRM — Production Guide

Руководство по развёртыванию и обслуживанию системы в production.

---

## 1. Переменные окружения

Обязательные (без них сервер не запустится или будет уязвим):

| Переменная | Пример | Описание |
|---|---|---|
| `SECRET_KEY` | `xk3$...50 случайных символов` | **Обязательно.** Генерация: `python -c "from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())"` |
| `DEBUG` | `False` | **Никогда** не ставьте `True` в production |
| `DATABASE_URL` | `postgresql://user:pass@host:5432/db` | Railway ставит автоматически |
| `ALLOWED_HOSTS` | `crm.example.com` | Домены через запятую |
| `CSRF_TRUSTED_ORIGINS` | `https://crm.example.com` | Origins через запятую (с `https://`) |

Первый директор (создаётся автоматически при старте, если директоров нет):

| Переменная | Описание |
|---|---|
| `INITIAL_DIRECTOR_USERNAME` | Логин первого директора |
| `INITIAL_DIRECTOR_PASSWORD` | Пароль (мин. 8 символов, проверяется валидаторами Django) |
| `INITIAL_DIRECTOR_NAME` | Опционально: «Имя Фамилия» |

Опциональные:

| Переменная | По умолчанию | Описание |
|---|---|---|
| `RUN_SEED_DATA` | `0` | `1` = создать demo-данные. **Только dev/staging!** |
| `LARGE_EXPENSE_THRESHOLD` | `5000` | Расход от этой суммы ($) уведомляет директоров |
| `WEB_CONCURRENCY` | `2` | Число воркеров Gunicorn |
| `SENTRY_DSN` | — | Включает мониторинг ошибок (см. раздел 8) |
| `AWS_STORAGE_BUCKET_NAME` и др. | — | Включает S3-хранилище медиа-файлов (см. раздел 4) |

## 2. Деплой на Railway

1. Подключите GitHub-репозиторий к Railway.
2. Добавьте PostgreSQL plugin — `DATABASE_URL` появится автоматически.
3. В Variables задайте: `SECRET_KEY`, `DEBUG=False`, `INITIAL_DIRECTOR_USERNAME`, `INITIAL_DIRECTOR_PASSWORD`.
4. Деплой запускает `start.sh`: collectstatic → migrate → create_initial_director → gunicorn.

**Важно:** `SECURE_SSL_REDIRECT` в Django не включён намеренно — Railway сам
редиректит HTTP→HTTPS на балансировщике. Включение в Django создаёт петлю редиректов.

### Как создать первого директора на production

Система **никогда** не создаёт demo-аккаунты автоматически в production —
это защита от входа под публично известным паролем. Первый директор создаётся
только из переменных окружения:

1. В Railway → web-сервис → **Variables** добавьте:
   - `INITIAL_DIRECTOR_USERNAME` — например, `ilhomjon`
   - `INITIAL_DIRECTOR_PASSWORD` — сильный пароль (мин. 8 символов, проверяется
     валидаторами Django: не только цифры, не слишком простой)
   - `INITIAL_DIRECTOR_NAME` — опционально, «Имя Фамилия»
2. Сохраните → Railway передеплоит. `start.sh` вызовет `create_initial_director`,
   который создаст директора **только если директора ещё нет** (идемпотентно).
3. Войдите под этими логином и паролем. После входа можно создавать остальных
   пользователей через интерфейс (Сотрудники → Новый пользователь).

Команда `seed_data` (demo-данные для всех ролей с паролем `demo123456`)
запускается **только** при `RUN_SEED_DATA=1` и предназначена исключительно для
локальной разработки. В production её ставить нельзя.

## 3. Backup PostgreSQL

### Ручной бэкап (Railway)

```bash
# Установите Railway CLI и залогиньтесь
railway login
railway link   # выберите проект

# Дамп всей базы
railway run pg_dump '$DATABASE_URL' --format=custom --file=backup_$(date +%Y%m%d).dump
```

Или напрямую, взяв `DATABASE_URL` из Railway Variables:

```bash
pg_dump "postgresql://user:pass@host:port/dbname" \
  --format=custom \
  --file=poytakht_backup_$(date +%Y%m%d_%H%M).dump
```

### Восстановление

```bash
pg_restore --clean --no-owner --no-privileges \
  --dbname="postgresql://user:pass@host:port/dbname" \
  poytakht_backup_20260101_1200.dump
```

### Автоматический бэкап — уже настроен

Вариант А — Railway сам делает снапшоты Postgres (проверьте тариф, работает
из коробки, но не даёт офсайт-копии).

Вариант Б (сделано в этом репозитории) — [.github/workflows/backup.yml](.github/workflows/backup.yml)
гоняет `pg_dump` каждую ночь в 02:00 UTC и кладёт дамп в Actions artifacts
(хранится 30 дней). **Чтобы это заработало, добавьте секрет в GitHub:**

1. Скопируйте `DATABASE_URL` из Railway → ваш Postgres-сервис → Variables.
2. В репозитории на GitHub: Settings → Secrets and variables → Actions →
   New repository secret → имя `DATABASE_URL`, значение — то, что скопировали.
   (Или из терминала, если стоит `gh`: `gh secret set DATABASE_URL`, вставить
   значение — так пароль от базы не попадёт в чат/историю команд.)
3. Проверить сразу, не дожидаясь ночи: вкладка Actions → DB Backup → Run workflow.

Восстановить дамп из артефакта: скачать zip со страницы прогона Action,
дальше — команда `pg_restore` ниже.

**Правило 3-2-1:** 3 копии, 2 разных носителя, 1 вне площадки. Сейчас есть:
рабочая база (1), Railway-снапшоты если включены (2), GitHub Actions artifact
(3, офсайт) — этого достаточно для малого бизнеса.

## 4. Медиа-файлы (квитанции, фото) — S3 хранилище

Файлы в `/media/` раздаются через `protected_media` с проверкой прав:
- Сотрудники видят все файлы.
- Клиенты — только квитанции своих платежей.

⚠️ На Railway файловая система **эфемерная** — без S3 загруженные файлы
пропадают при каждом редеплое.

**Уже подключено в коде** (django-storages + boto3), включается переменными
окружения — без них ничего не меняется, всё как раньше (локальный диск):

| Переменная | Обязательна | Пример |
|---|---|---|
| `AWS_STORAGE_BUCKET_NAME` | да | `poytakht-crm-media` |
| `AWS_ACCESS_KEY_ID` | да | из вашего S3/R2/B2 аккаунта |
| `AWS_SECRET_ACCESS_KEY` | да | из вашего S3/R2/B2 аккаунта |
| `AWS_S3_ENDPOINT_URL` | только для R2/B2 | `https://<account>.r2.cloudflarestorage.com` (для настоящего AWS S3 — не задавать) |
| `AWS_S3_REGION_NAME` | нет | `auto` по умолчанию |

Рекомендация для небольшого бизнеса — **Cloudflare R2**: 10 ГБ бесплатно,
без платы за исходящий трафик (в отличие от AWS S3), S3-совместимый API
подходит без изменений в коде.

Как только переменные заданы — просто передеплойте, новые загрузки пойдут
в бакет. **Старые файлы, уже лежащие на диске Railway, сами не переедут** —
если они ещё живы (редеплоя не было), их надо будет скопировать вручную
(могу помочь отдельным скриптом, когда бакет будет готов).

## 5. Безопасность — чеклист перед запуском

- [ ] `DEBUG=False`
- [ ] `SECRET_KEY` — уникальный, 50+ символов, не из репозитория
- [ ] `.env` не закоммичен (проверьте `.gitignore`)
- [ ] Пароль директора сменён с демо на реальный (теперь это можно сделать и
      в самом приложении — Профиль → Сменить пароль, или директор/админ →
      Сотрудники → Пароль для любого управляемого пользователя)
- [ ] `RUN_SEED_DATA` не установлен (или `0`)
- [ ] HTTPS работает (Railway даёт из коробки)
- [ ] Секрет `DATABASE_URL` добавлен в GitHub (Settings → Secrets → Actions) — иначе ночной бэкап падает
- [ ] Восстановление бэкапа хоть раз проверено на тестовой базе
- [ ] `SENTRY_DSN` задан (см. раздел 8) — иначе о падении сайта вы узнаете только от клиента
- [ ] `AWS_STORAGE_BUCKET_NAME` и ключи заданы, если храните реальные квитанции/фото (иначе они пропадут при следующем редеплое)
- [ ] `python manage.py check --deploy` — без критических предупреждений

## 7. Роли и доступ

| Роль | Доступ |
|---|---|
| Директор | Всё |
| Гл. администратор | Всё кроме управления пользователями |
| Менеджер | Квартиры, клиенты, продажи, брони, платежи (без расходов/прибыли/отчётов) |
| Бухгалтер | Платежи, расходы, отчёты, зарплаты |
| Прораб | Рабочие, посещаемость, материалы |
| Складовщик | Материалы, поставщики, движение |
| Клиент | Только свой кабинет: квартира, платежи, долг |

## 8. Мониторинг ошибок (Sentry)

Без этого о падении страницы с 500-ошибкой вы узнаете только когда позвонит
клиент — логи есть только в консоли Railway, никто их активно не читает.

1. Зарегистрируйтесь на [sentry.io](https://sentry.io) (бесплатный тариф
   достаточен для небольшого проекта), создайте проект типа Django.
2. Скопируйте DSN (выглядит как `https://xxx@xxx.ingest.sentry.io/xxx`).
3. В Railway → Variables добавьте `SENTRY_DSN` с этим значением, передеплойте.
4. Готово — ошибки 500 и необработанные исключения будут прилетать в Sentry
   с трейсбеком, без персональных данных пользователей (`send_default_pii=False`).

## 9. Удаление объектов (комплексы/блоки/этажи/квартиры)

Удаление доступно директору и админу. Защищено от потери финансовой истории:
если по квартире (или по любой квартире внутри этажа/блока/комплекса) когда-либо
была продажа или бронирование — удалить нельзя, приложение покажет, какие именно
квартиры блокируют удаление. Продажи в этом приложении никогда не удаляются
физически (только отменяются с сохранением записи) — то же самое правило
применяется и здесь: если жалко данные о деньгах, значит и удалить нельзя.

Удалять можно свободно только то, что никогда не продавалось и не бронировалось —
например, ошибочно сгенерированные через «Массовое создание» квартиры.

## 10. Смена/сброс пароля

- Любой пользователь: Профиль → «Сменить пароль» (нужно знать старый).
- Директор/админ для менеджера или бухгалтера: Сотрудники → кнопка «Пароль»
  у нужного пользователя (старый пароль знать не нужно).
- Свой пароль директор/админ тоже меняет через Профиль, не через список пользователей.
